## 1. 目的

Phase 1（Web／PWA）存在的唯一目的是驗證產品價值，不是最終形態。在投入 Phase 2（Native iOS）工程成本之前，先由產品作者本人（Jenny）日常實際使用 Phase 1，確認《等等看》的核心假設——「收藏比整理重要、找得回比收藏多重要、重新相遇比提醒重要」——在真實生活中是否成立。

本文件是「是否開始 Phase 2 Native」的唯一判準來源。工程不得在本文件判定完成前假設 Phase 2 一定會發生，也不得在判定不成功時逕自開始 Native 開發。

## 2. MVP 目標

Phase 1 的 MVP 目標不是「功能完整」，而是「作者本人願意持續使用，並取代目前分散的收藏習慣」：

- Jenny 使用《等等看》Web App 取代目前分散於瀏覽器書籤、社群收藏、聊天室與截圖的收藏行為。
- 收藏動作足夠輕量，不會因為「還要開電腦／找網址」而放棄收藏。
- Daily Recall 讓 Jenny 主動打開 App 重新看看收藏，而不是被閒置的功能。
- 備份／還原流程讓 Jenny 敢於信任「資料不會不見」，願意持續累積收藏而不用另外做保險備份。

## 3. 驗證項目（觀察指標，不設固定數字）

Phase 1 先累積真實使用資料，再訂 KPI；本輪**不預設任何固定天數、比例或次數門檻**。以下六項以觀察指標描述，觀察的是「方向」與「趨勢」，不是「數字達標與否」。

| # | 觀察指標 | 觀察方式（質性） |
|---|---|---|
| 1 | 收藏是否持續增加 | 觀察收藏總筆數與新增頻率的長期趨勢，重點是「有沒有持續在用」，不是特定一天收藏幾筆。 |
| 2 | Recall 是否自然被使用 | 觀察 Jenny 是否會主動打開「今日回顧」，而不需要刻意提醒自己去用；是否逐漸變成日常習慣的一部分。 |
| 3 | 收藏是否重新被閱讀 | 觀察收藏內容是否曾被重新打開（`lastOpenedAt` 有更新），而不是收藏後就再也沒看過；這是「找得回」價值是否成立的直接訊號。 |
| 4 | 分類是否逐漸穩定 | 觀察分類使用方式是否隨時間收斂成幾個穩定、常用的分類，還是持續混亂、「未整理」佔比長期居高不下。 |
| 5 | 洞洞板是否形成固定使用方式 | 觀察洞洞板是否發展出 Jenny 自己的使用習慣（例如固定拿來放某類內容、固定會回去看），而不是建立後就被遺忘的功能。 |
| 6 | 備份是否讓使用者有安全感 | 觀察 Jenny 是否因為信任備份／還原流程而放心持續收藏，不需要另外自行做保險備份；至少完整演練過一次匯出／匯入／還原，確認不會造成資料遺失或不敢信任的狀況。 |

## 4. 觀察期間與方法

- **不設固定觀察期。** 不使用「連續幾週」之類的時間門檻；Phase 1 完成 `P1-C3` 後即開始持續觀察，直到 Jenny 認為已累積足夠真實使用經驗，足以對上述六項指標做出有把握的判斷為止。
- 觀察方法：
  - 產品內既有的本機統計（收藏總筆數、最近備份日期、分類分佈、`lastOpenedAt` 分佈）。
  - Jenny 主觀記錄（簡單日誌或印象整理，不需要逐日打卡）。
  - 匯出 JSON／CSV 後人工檢視資料分佈與趨勢。
- Phase 1 不建置自有後端，不假設有伺服器端事件分析（與 PRD §14 Success Metrics 原則一致）。
- 觀察期間允許同步修正 Phase 1 產品問題（文案、流程小卡點）；這是預期中的正常迭代，不代表驗證失敗，也不需要因此重新起算觀察。

## 5. 成功條件（趨勢方向，不是固定門檻）

Phase 1 驗證成功，指六項觀察指標的**趨勢**皆朝正向發展：

- 收藏行為隨時間持續發生，且是 Jenny 主動、自然的習慣，不需要外部提醒才想起來用。
- Daily Recall 逐漸變成 Jenny 會自己主動查看的日常環節，而非被忽略的功能。
- 收藏內容確實會被重新打開、重新看到，證明「找得回」比單純「收藏」更有價值。
- 分類使用方式隨時間收斂、變得可預期，不再持續混亂。
- 洞洞板發展出 Jenny 自己認得出來的使用方式，而不是空著或被遺忘。
- Jenny 對備份／還原流程有信心，且至少完整驗證過一次不會造成資料遺失。

具體數字門檻（例如「多少比例的天數有收藏」）刻意不在本輪設定；待 Phase 1 累積足夠真實使用資料、對正常範圍有實際基準後，再依 §7「KPI 訂定時機」另行制定可衡量的 KPI。

## 6. 不成功條件

出現以下任一情況，即視為本輪驗證不成功，**不得**進入 Phase 2 Native：

- 收藏行為隨時間趨緩、停滯或逐漸被放棄，而非持續或成長。
- Daily Recall 長期被忽略，Jenny 幾乎不會主動查看。
- 收藏內容持續累積但幾乎不曾被重新打開，代表「找得回」的核心價值沒有真正成立。
- 分類長期停留在混亂狀態，「未整理」持續佔絕大多數，Jenny 對分類方式感到困惑而非放心。
- 洞洞板始終沒有形成任何固定使用方式，形同虛設。
- 備份／還原流程在任何一次演練中發生資料遺失、損毀，或讓 Jenny 感到不敢信任——**此項為阻擋性條件**：即使其餘五項都朝正向發展，只要備份出現這類問題，仍視為不成功。
- Jenny 主觀認定「這個產品沒有讓我想繼續用」。

## 7. 判定與治理

- 判定人為 Jenny 本人；本文件不引入任何自動化評分、固定 KPI 或第三方分析工具做判定依據。
- **判定時機由 Jenny 自行決定**——當她認為已經累積足夠真實使用經驗，能對六項觀察指標做出有把握的判斷時，即可進行判定，不受限於任何預設的觀察期長度。
- 判定時，由 Jenny 對照 §5／§6 逐項描述目前趨勢，並在 `DECISION_LOG.md` 新增一筆「Product Validation 判定結果」決策條目，記錄：判定日期、逐項觀察結果、是否成功、若不成功則後續修正方向。
- **KPI 訂定時機：** 待累積足夠真實使用資料、對六項指標的正常範圍有實際基準後，才回頭將部分觀察指標轉為具體可衡量的 KPI（例如具體的收藏頻率、回顧比例），並以新的 Decision Log 條目正式記錄；不在 Phase 1 一開始就預設數字，也不得為了「有數字比較好看」而回頭假造基準。

## 8. 進入 Phase 2（Native）的條件

- **只有 §5 描述的正向趨勢全部成立，且 §6 沒有任何不成功條件觸發，才可啟動 Phase 2（Native iOS）`P2-C1 Native Foundation`。**
- 判定不成功時，先回到 Phase 1 修正產品或流程（例如簡化收藏輸入、調整分類預設、強化備份體驗），持續觀察至趨勢改善後再重新判定；不得直接跳至 Native 開發，也不得以「反正之後都要做 Native」為由跳過本輪判定。
- Phase 2 啟動時，`docs/adr/0001-phase1-slice1-persistence.md` 與 `docs/engineering/phase1-slice1-project-plan.md` 為現成的技術分析與執行 Runbook，可直接接續審閱，不需重做。
